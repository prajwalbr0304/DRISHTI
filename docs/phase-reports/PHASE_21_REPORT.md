## 12. Remaining tracked item

The one remaining closure is the **crime-domain operational WRITE path** to
Catalyst Data Store:

- `intake` FIR create/submit/approve (18-digit CrimeNo, party roles, versioning,
  state machine), `casework` court/disposition/lifecycle transitions, and the
  `imports` commit/canonicalization pipeline still WRITE to the AWS RDS serving
  schema (exercised by the `@requires_db` DB pass, rolled back).

Why it is separated, not rushed: these are the most complex, most heavily-tested
canonicalization write paths in the platform. Rewriting them to the Data Store
repository model is a large, high-regression-risk change that cannot be
completed AND verified safely in one phase without endangering the working
codebase. The READ side of every one of these domains is already Data
Store-backed and DB-free, and the interactive demo WRITE surfaces (Investigation
Board, Disaster Response) are Data Store-native today.

Completion path: convert each write path to `app/datastore/repository.py`
(upsert-by-ExternalID, reusing `mapping.py` identifiers), add Data Store write
contract tests, then the `@requires_db` markers on those write tests can be
retired. Until then the demo runs read-centric with Board/Disaster interactive
writes, which is HACKATHON-DEMO READY.

Completed this phase (was pending): route-boundary inventory + enforcement; the
six-role Gateway mapper + matrix; disaster schema + provisioner; the mandatory
Signal + forecast cron; readiness gating; the protected analytics adapter; the
money authorization matrix moved off RDS into code; and the operational
READ/reference/lookup closure for intake, casework, imports, admin and the
financial views to Catalyst Data Store (seeded from the serving-export subset).

No local fakes, screenshots or config files were counted as cloud evidence; no
Catalyst/AWS resources were provisioned in this phase.
